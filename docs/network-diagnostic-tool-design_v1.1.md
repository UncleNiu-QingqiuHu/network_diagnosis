## 2. 实现形态（已定）

- **桌面 GUI**：面向运维/技术支持的单机工具，本地执行探测与（可选）抓包，结果在界面展示并可导出报告。
- 编排逻辑（校验目标 → 可选起抓包 → tcping/其它探针 → 汇总）由 GUI 应用驱动；**不依赖用户自行配置 PATH 来找到 tcping**（见第 4、8 节）。

---

## 3. 产品目标（三类，已定）

| 类别 | 含义 | 主要手段（规划） |
|------|------|------------------|
| **网络连通性** | 本机到目标是否「能到达」、名字能否解析、路径大致是否通 | DNS 解析；ICMP ping（可选，受防火墙影响）；可选 traceroute |
| **网络质量** | 延迟与稳定性，而非仅「通/不通」 | 多次采样 RTT（ping / tcping）；抖动、成功率（等价丢包倾向）；可选结合抓包看重传 |
| **端口连通性** | 指定 TCP 端口是否开放、握手是否完成、拒绝或黑洞形态 | **tcping.exe**（项目内置），按端口批量/串行探测 |

**典型场景**（继承 v1.0）：公网/内网端口是否通、DNS 是否正常、中间设备 RST/黑洞、为上层协议问题建立基线。

## 4. tcping 集成策略（已定）

- **tcping 可执行文件随项目分发**（安装目录或应用目录下固定相对路径调用），**不依赖**用户本机是否单独安装 tcping、也不依赖 PATH。
- 版本锁定：发布包内附带**固定版本**的 `tcping.exe`，并在「关于/诊断信息」中展示该版本，便于排障与解析输出格式。
- 调用与解析要求仍适用 v1.0：子进程、超时、多次采样、优先机器可读输出、IPv4/IPv6 策略、归档原始 stdout/stderr。

---

## 5. tshark 是否推荐集成到项目（不依赖用户环境）

### 5.1 结论（推荐原则）

- **推荐**：在**许可证、安装包体积、维护成本**可接受的前提下，**随应用分发固定版本的 `tshark`（及官方要求的配套 DLL/插件最小集）**，由程序用绝对路径调用，避免「用户没装 Wireshark / 版本不一 / PATH 未配置」。
- **需要向用户诚实说明**：在 **Windows** 上，要进行**与普通 Wireshark 相同的网卡抓包**，通常仍依赖 **Npcap**（或历史环境里的 WinPcap）这类**抓包驱动**。驱动安装在多数机器上属于**系统级变更**，受企业策略限制；因此 **「完全不依赖用户环境」在抓包能力上往往无法 100% 成立**，只能保证 **「不依赖用户自己去装 Wireshark CLI」**。
- **产品策略建议**：
  - **核心能力**（连通性 + 质量 + 端口）：仅靠内置 tcping + （可选）系统 ping 即可，**不强依赖**抓包。
  - **增强能力**（自动 pcap、握手/RST/重传等事实提取）：在检测到 **Npcap 可用 + 自带 tshark 可运行** 时启用；否则 **降级**：明确提示「抓包不可用，仍可进行端口/延迟类诊断」，并引导可选安装 Npcap（若贵司安装程序允许捆绑或可选组件）。

### 5.2 集成 tshark 的额外收益与代价

| 方面 | 说明 |
|------|------|
| 收益 | 版本锁定、可重复、支持自动化起止抓包与写 `pcapng`、与 tcping 时间窗对齐 |
| 代价 | 安装包显著增大；Wireshark/tshark 遵循 **GPL** 等许可，需合规随附版权声明与源码获取方式（具体以实际捆绑方式由法务确认） |
| 若不集成 tshark | 需假设用户已安装 Wireshark 并配置 PATH，**与「不依赖用户环境」目标冲突**；或完全不做链路层抓包 |

### 5.3 与 v1.0 的关系

- 自动化抓包仍以 **tshark（CLI）** 为主，GUI 的 Wireshark 仅作「可选打开 pcap」；v1.0 中表格与参数规范继续有效。
- v1.0 第 8 节「路径」在 v1.1 中收敛为：**tcping、tshark 均由应用内置路径解析**；Npcap 仍为**可变/外部**依赖，除非安装器一并处理。

## 6. 诊断应从哪些维度开展（建议清单）

下列维度可按 **「本地环境 → 名字与路由 → 连通与质量 → 端口 → 可选抓包事实」** 顺序在 GUI 中分区展示，便于用户自上而下缩小范围。

### 6.1 本机与出口上下文（Local Context）

- **活动网卡**：名称、类型、是否启用；可选：当前选用哪块网卡做探测（高级）。
- **本机 L3 信息**：IPv4/IPv6 地址、子网掩码前缀、**默认网关**。
- **DNS 配置**：当前系统使用的 DNS 服务器列表（仅展示事实，不替代解析测试）。
- **备注**：若存在多网卡/VPN/代理，可用简短提示「结果仅代表当前路由选路下的路径」（代理深层检测可后延）。

### 6.2 名字解析（DNS）

- **解析结果**：A / AAAA 记录、解析到的 IP 列表；解析耗时。
- **失败形态**：NXDOMAIN、超时、无响应等（取决于实现）。
- **与探测一致**：端口与质量类探针实际使用的目标 IP（及地址族）应在报告中写明，避免域名解析变化造成误解。

### 6.3 基础连通性（Reachability）

- **ICMP Ping**（可选模块）：若目标允许 ICMP，可看是否可达；若不允许，界面需标注「ICMP 被禁不代表 TCP 不通」。
- **Traceroute**（可选、进阶）：路径上每一跳的时延与是否超时，辅助判断阻断大致区段；实现成本与权限需单独评估，可作为 v1.x 之后能力。

### 6.4 网络质量（Quality）

- 基于 **多次 ping**（若启用）与 **每端口多次 tcping**：
  - **RTT**：最小 / 平均 / 最大（或百分位，可后延）。
  - **成功率**：成功次数 / 总次数，作为**连通稳定度**指标。
  - **抖动**：相邻 RTT 差分的统计（简易 jitter），用于粗评稳定性。
- **说明**：质量结论应区分「ICMP 质量」与「TCP 某端口质量」，二者可能不一致。

### 6.5 端口连通性（Port / Service Reachability）

- 针对用户输入的每个端口：
  - **是否完成 TCP 握手**（或 tcping 定义的等价成功条件）。
  - **失败分类**（依据 tcping 输出与可选抓包）：超时（似黑洞）、RST（似拒绝或未监听）、其它异常。
  - **该端口的 RTT 与成功率**（与 6.4 对齐展示）。

### 6.6 抓包层事实（可选，依赖 Npcap + 自带 tshark）

在抓包成功且与探针时间对齐的前提下，可提供**确定性事实**（不过度解读应用层）：

- 是否观察到 **SYN / SYN-ACK / RST / FIN** 等与本次端口相关的报文。
- **重传**是否存在（粗粒度计数或标记）。
- 输出 **pcapng 路径** 供人工在 Wireshark 中深入分析。

启发式结论（防火墙 vs 未监听等）仍建议标注置信度，见原 v1.0「自动化程度分层」。

### 6.7 报告与可观测性（元数据）

- **任务 ID、时间范围**、每段探测起止时间、所用**内置 tcping/tshark 版本**、是否启用抓包及是否降级。
- 原始**控制台输出**归档路径或内嵌片段，便于售后复现。

## 7. 总体编排思路（继承并贴合 GUI）

1. **解析与校验**目标与端口列表；可选先跑 DNS 并展示 6.2。
2. **（可选）** 若用户勾选抓包且环境允许：按 v1.0 规范启动 tshark。
3. **执行探针**：ping（可选）→ 按端口 tcping（串行多端口建议默认保留）。
4. **停止抓包**并落盘；汇总 6.x 各维度到 GUI 与导出报告。
5. **降级路径**：任一步失败时明确 UI 状态与可操作指引（尤其 Npcap、tshark 启动失败）。

---

## 8. 依赖、分发与合规（v1.1 更新）

- **tcping**：与主程序一起发布，相对路径加载。
- **tshark**：推荐随包分发**固定版本**；GPL 合规与第三方通知必不可少。
- **Npcap**：作为**抓包能力的常见外部依赖**，通过安装器可选组件或文档引导处理；无法在纯用户目录下「仅拷贝 exe」完全替代。
- **企业环境**：不允许安装 Npcap 时，产品仍应在**无抓包**模式下完整提供 6.1～6.5 的核心价值。

---

## 9. 第一版范围（MVP，相对 v1.0 微调）

- 桌面 GUI；输入目标、端口列表、次数/超时、可选 IPv4/IPv6 策略。
- 内置 tcping；展示 **6.2（DNS）+ 6.5（端口）** 为必需；**6.4（质量）** 至少基于 tcping 多样本；**6.3 ping** 建议 MVP 即做（系统 ping 或自带组件择定）。
- 抓包：**有条件启用**（自带 tshark + 检测到 Npcap），失败则降级并清晰提示。
- 报告：导出一份结构化结果（JSON 或 HTML 择一亦可）+ 原始日志引用路径。

## 10. 待拍板的产品决策（v1.1 未决缩小后）

1. **tcping 语义**：仅完成握手，还是建立到应用层可读状态（若工具支持）？
2. **抓包粒度**：单次任务单 pcap vs 每端口 pcap。
3. **安装器策略**：是否官方捆绑/可选安装 **Npcap**，以及是否需要 **管理员权限** 安装向导。
4. **技术栈**：桌面 GUI 框架（如 .NET WPF/WinUI、Qt、Electron 等）与单文件/安装包大小上限。
5. **ICMP/traceroute**：MVP 是否包含系统 `ping`，traceroute 是否排入 v1.2。
