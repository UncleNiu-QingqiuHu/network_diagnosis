# 数据库诊断功能方案（MySQL / PostgreSQL / SQL Server / Oracle / SQLite3）

本文档在「慢查询、索引、闩锁/锁」等方向之外，整理**多引擎数据库诊断**的维度与落地思路，约定 **Markdown 诊断报告** 的生成要求，并补充 **数据库性能实时监控** 的产品方案。实现时以本仓库代码与后续选型的驱动为准。

---

## 1. 支持的数据库引擎

| 引擎 | 典型部署形态 | 诊断侧重（摘要） |
|------|----------------|------------------|
| **MySQL** / **MariaDB** | 单机、主从、Group Replication | `performance_schema`、`sys` 库、InnoDB 状态、复制延迟 |
| **PostgreSQL** | 单机、流复制、Patroni 等 | `pg_stat_*`、等待事件、`EXPLAIN`、WAL、复制槽 |
| **SQL Server** | 单机、AG、Always On | DMVs、等待统计、阻塞/死锁、`tempdb`、错误日志 |
| **Oracle** | RAC / 单实例 | AWR/ASH（若授权）、`V$` 视图、等待事件、表空间 |
| **SQLite3** | 嵌入/文件 | 无独立服务端：侧重 **文件完整性**、**连接与锁**、**PRAGMA**、**慢查询（应用层）** |

**原则**：同一套「诊断维度」抽象到产品层，底层按引擎分发 **采集 SQL / 命令** 与 **结果解析**；SQLite3 能力显著弱于 C/S 型数据库，报告中需明确 **能力边界**。

---

## 2. 诊断维度总览（与慢查询/索引/闩锁并列）

下列与先前讨论的「慢查询、索引检查、闩锁诊断」**互补**，按类别组织。

### 2.1 性能

| 维度 | 说明 | 引擎差异提示 |
|------|------|----------------|
| 慢查询 | Top SQL、耗时分布、执行次数；必要时脱敏绑定参数 | MySQL/PG/SQL Server/Oracle 均有系统视图或接口；SQLite 依赖应用日志或 `EXPLAIN QUERY PLAN` |
| 执行计划与优化器 | 计划稳定性、估计行数偏差、统计信息是否陈旧 | Oracle SQL Server 计划缓存较成熟；PG `EXPLAIN (ANALYZE, BUFFERS)`；MySQL `EXPLAIN`/`optimizer_trace` |
| 等待事件 / 资源等待 | 将瓶颈从「某条 SQL」落到「在等什么」 | SQL Server `sys.dm_os_wait_stats`；PG `pg_stat_activity.wait_event_type`；Oracle `V$SESSION`/`ASH`；MySQL 以 mutex/lock P_S 为主 |
| I/O 与缓冲 | 读延迟、Checkpoint、缓冲池压力 | 各库指标名不同，宜做「归一化标签」写入报告 |
| 临时空间 | 排序/哈希溢出、`tempdb`、临时文件 | SQL Server `tempdb`；PG `temp_files`；MySQL `tmpdir`/内部临时表 |
| 后台维护 | 统计信息更新、索引维护窗口与业务高峰重叠 | 策略类条目可来自配置 + 最近一次 analyze 时间 |

### 2.2 并发与一致性（含闩锁 / 锁）

| 维度 | 说明 |
|------|------|
| 锁与阻塞 | 谁阻塞谁、持锁时长、阻塞链 |
| 死锁 | 死锁图/死锁日志摘要（可截断） |
| 闩锁 / 轻量级锁 | SQL Server `LATCH_*`；MySQL InnoDB mutex/ rw-lock（偏底层）；Oracle latch；PG 相对少强调 latch 一词，多用 LWLock |
| 隔离级别与长事务 | 未提交事务、长时间 idle in transaction |
| 连接与会话 | 会话数、连接池上限、每库连接分布 |

### 2.3 容量与可靠性

| 维度 | 说明 |
|------|------|
| 存储空间 | 数据文件/表空间/数据库大小、剩余空间、增长趋势 |
| 日志与恢复 | 日志切换、WAL 积压、备份链、恢复模式（概念对齐各库） |
| 复制与高可用 | 主从/AG 延迟、延迟_sec、last error（按可用性采集） |

### 2.4 结构与数据质量

| 维度 | 说明 |
|------|------|
| 索引 | 缺失索引建议、未使用索引、冗余索引、碎片/膨胀（引擎相关） |
| 统计信息 | 陈旧度、直方图/多维统计（若可获取） |
| 约束与完整性 | 外键未启用、不信任约束（SQL Server）、孤儿数据风险（采样或离线） |
| 一致性检查 | `DBCC`、逻辑备份校验、SQLite `integrity_check` |

### 2.5 安全与合规（可选模块）

| 维度 | 说明 |
|------|------|
| 账户与权限 | 高危角色、默认账户、横向权限过大 |
| 网络与加密 | 是否强制 TLS、监听地址 |
| 审计 | DDL/登录失败（视版本与插件） |

### 2.6 可观测性与基线

| 维度 | 说明 |
|------|------|
| 基线对比 | 同指标「平时 vs 当前」 |
| 历史趋势 | QPS、延迟分位、Top 等待、主要库表体积增速（与现有网络诊断「历史对比」思路一致） |

### 2.7 SQLite3 特有能力边界（须在报告声明）

- 无独立服务端进程时：**无集群复制、无全局等待统计**；重点为 **文件路径、锁定、journal 模式、`PRAGMA quick_check`/`integrity_check`**、**数据库页统计**、**应用侧慢 SQL**。
- 若 SQLite 在 WAL 模式：**`-wal` / `-shm`** 文件状态可简要记录。

## 3. 架构建议（与现有项目对齐）

1. **连接抽象**：JDBC/ODBC 或各语言官方驱动；统一 **连接串 + 凭据（不落盘明文）**、超时、只读会话偏好。  
2. **采集层**：每引擎实现「采集器」接口：输入连接与选项，输出 **结构化结果**（JSON 友好 dataclass）。  
3. **编排层**：选择诊断项（全量/自定义），控制并行度与总时长上限。  
4. **报告层**：见第 4 节，**统一生成 Markdown**，并可选用与网络诊断相同的 `reports/` 目录约定。  
5. **监控层（可选）**：见第 5 节，**固定周期轻量采集** + GUI 实时展示；与「一次性深度诊断」解耦，共用连接抽象与部分归一化指标。  
6. **风险**：生产库采集需 **显式用户确认**、**限流**、**避免重型查询**（如全表扫描类 `CHECKDB` 默认关闭或独立开关）。

## 4. Markdown 诊断报告生成

### 4.1 目标

- 每次「数据库诊断」任务生成 **至少一份 Markdown 文件**，便于归档、发邮件、进工单系统。  
- 风格与现有 **网络诊断 Markdown 报告** 协调：同级标题、列表、表格、代码块（SQL/配置片段）、**敏感信息脱敏**。

### 4.2 建议文档结构（模板）

```markdown
# 数据库诊断报告

## 元信息
- 任务 ID / 生成时间（UTC+8）
- 目标引擎与版本（例：PostgreSQL 16.2）
- 连接信息：**脱敏**（仅主机名+库名，无密码）
- 诊断项勾选列表与采集耗时
- 工具版本（与网络诊断的 APP_VERSION 一致或可并列）

## 执行摘要
- 结论分级（正常 / 注意 / 严重）与一句话摘要
- Top 3 风险与建议动作

## 环境与会话
- 服务器标识、时区、主要配置参数（白名单字段）
- 当前会话数 / 最大连接（若可获取）

## 性能
### 慢查询 / 语句统计
- 表格或 TopN 列表（阈值可配置）
### 等待 / 资源
- 归一化后的等待分类（各引擎映射表）
### I/O 与缓冲（若采集）
- 摘要指标

## 并发
### 阻塞与锁
- 阻塞链摘要或列表
### 死锁（节选）
### 闩锁 / 轻量级同步（按引擎）

## 容量与存储
- 库/表空间/文件大小
- 增长与剩余空间

## 高可用与复制（若适用）
- 角色、延迟、错误信息节选

## 索引与统计
- 缺失/冗余索引建议（注明来源视图）
- 统计信息陈旧对象（TopN）

## 一致性与完整性（若执行）
- `integrity_check` / 校验结果摘要

## SQLite 专节（若引擎为 SQLite）
- 文件路径、页大小、journal 模式、WAL 存在性
- `PRAGMA` 摘要

## 原始与扩展
- **原始结果路径**（JSON/CSV 可选，与网络诊断类似的 `report_dir`）
- 未执行项及原因（权限不足 / 超时 / 用户关闭）

## 免责声明
- 只读/影响说明；结论需结合业务与 DBA 复核
```

### 4.3 脱敏与安全

- 连接串中的 **密码、密钥** 不出现在 Markdown。  
- SQL 文本中的 **字面值常量** 可按规则打码（可选开关）。  
- 主机名、IP 是否脱敏由配置控制。

### 4.4 与仓库集成要点

- **输出目录**：建议复用或扩展 `report_root()` 下子目录，例如 `reports/db_diagnosis/<task_id>/`。  
- **文件名**：`db-diagnosis_<timestamp>_<engine>.md` 或与网络诊断同一命名风格。  
- **关联**：若一次「运维会话」中同时跑网络诊断与数据库诊断，可在各报告元信息中互链任务 ID。  
- **与实时监控的关系**：监控运行中可 **按用户操作** 导出「监控片段」Markdown（见第 5.5 节）；深度诊断任务仍以第 4 节整份报告为主。

## 5. 实时监控（数据库性能）

### 5.1 定位与边界

| 对比项 | 一次性诊断（第 2～4 节） | 实时监控（本节） |
|--------|--------------------------|------------------|
| 目的 | 全面采集、生成完整 Markdown 报告 | **持续观察**关键指标变化，快速感知尖峰、阻塞、复制掉队 |
| 查询重量级 | 可含较多只读查询（仍受开关与超时约束） | **仅轻量、短查询**；默认禁止全表扫描类采集 |
| 输出 | 单次任务结束产出报告 | **主界面动态刷新**；可选导出阶段性 Markdown |

实时监控 **不替代** 专业 APM/数据库厂商监控平台，而是桌面工具内的 **轻量哨兵**，适合排障时「盯一会儿」库况。

### 5.2 能力与引擎映射（归一化指标示例）

产品层对外展示 **统一名称**，底层按引擎映射到具体视图/SQL（实现阶段再固化语句）。

| 归一化指标 | MySQL / MariaDB | PostgreSQL | SQL Server | Oracle | SQLite3 |
|------------|-----------------|--------------|------------|--------|---------|
| 活跃会话 / 连接数 | 线程/连接相关状态 | `pg_stat_activity` 计数 | `dm_exec_sessions` 等 | `V$SESSION` | 连接句柄数（弱） |
| 当前等待 / 状态 | P_S 摘要（版本相关） | `wait_event` 分布摘要 | 会话等待 + wait stats 快照 | `V$SESSION` 等待类 | 通常 N/A |
| 阻塞会话数 | information_schema / P_S | 锁阻塞查询（轻量） | 阻塞链 DMVs | 阻塞视图 | 数据库锁（文件级） |
| 复制 / HA 延迟 | 复制状态字段 | 复制滞后 | AG/同步视图 | Data Guard 等（视权限） | N/A |
| 吞吐代理 | QPS/Questions、Handler（节选） | `pg_stat_database` 增量 | Batch Requests 等计数器增量 | `V$SYSMETRIC` 等（视权限） | N/A |
| 存储 / 空间 | 表空间/库大小（周期不必过频） | 数据库大小、表膨胀提示 | 文件大小 DMV | 表空间使用率 | 文件字节数、`page_count` |

**SQLite3**：监控页限于 **文件大小、页数、journal/WAL 模式、完整性快速检测（低频）**；不做「集群级」指标。

### 5.3 交互与刷新策略（GUI）

- **刷新间隔**：用户可选（如 1 / 2 / 5 / 10 / 30 秒），默认 **5 秒**；防止对生产库构成压力。  
- **暂停 / 继续**：避免切屏时后台仍狂刷。  
- **连接**：建议 **长连接 + 合理 statement/query 超时**；断开时优雅释放。  
- **线程模型**：与现有网络诊断 GUI 一致，**工作线程采集 + 队列回灌/UI `after`**，避免阻塞 Tk 主线程。  
- **展示形式**：表格（当前 Top 等待、阻塞列表摘要）+ 可选简易折线（内存中保留最近 *N* 个点，不写数据库）。  
- **告警高亮（可选）**：阈值越过时状态条变色（如阻塞数 > 0、复制延迟 > *X* 秒），不默认弹窗轰炸。

### 5.4 负载与风险控制

- 每次 tick **查询数量与总耗时上限**（如单 tick 合计 < 300～500 ms，可配置）。  
- **降频**：连续超时或错误则自动加大间隔或暂停并提示。  
- **权限**：监控账号建议 **仅监控所需最小权限**（各引擎文档单独列出）。  
- **与深度诊断互斥**：同连接或同实例上可选「监控运行时锁定重量级诊断按钮」，避免叠加压力。

### 5.5 监控片段导出 Markdown

- **触发**：用户点击「导出当前监控摘要」或停止监控时可选「保存会话摘要」。  
- **内容建议**：时间范围、采样间隔、引擎与版本（脱敏连接信息）、每个归一化指标的 **首尾值 / 最大最小**、阻塞峰值时刻的 **行数快照**、异常报错节选。  
- **存储路径**：与第 4.4 节同族，例如 `reports/db_monitor/<task_id>/monitor-snapshot_<timestamp>.md`。  
- **说明**：该文件是 **时段摘要**，不等同于第 4 节全量诊断报告；二者可在元信息互链。

### 5.6 与一次性诊断、网络诊断的协同

- **诊断**：用于「拍 CT」— 全面、可归档。  
- **监控**：用于「看心电图」— 连续、轻量。  
- 若同时关心 **应用 host 与数据库**，可在后续版本中在报告元信息互链「同次排障会话 ID」（与网络诊断报告对齐思路）。

## 6. 落地优先级建议

1. **MySQL + PostgreSQL + SQL Server**：社区资料与 `information_schema` / DMV 生态成熟，先覆盖「会话/锁/慢查询/索引/空间」的只读采集 + Markdown；**实时监控**可先上 **会话/阻塞/复制延迟** 等 3～5 个轻量指标。  
2. **Oracle**：依赖环境与授权差异大，先做 **V$ 会话/锁/表空间/等** 子集，AWR 另议；监控同样以 **会话、阻塞、表空间** 快照起步。  
3. **SQLite3**：**完整性检查 + PRAGMA + 文件元数据** + 报告专节，避免与 C/S 库功能强行对齐；监控只做 **文件与 PRAGMA 低频采样**。
